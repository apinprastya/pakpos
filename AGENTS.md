# AGENTS.md

Guidance for AI coding agents working on **Pakpos**, a desktop REST API client (a Postman-style tool, REST only) built with Go + Wails v3 and React/TypeScript.

Read before larger changes:
- `docs/ARCHITECTURE.md`: decisions and layering
- `docs/PLAN-TIER1.md`: current milestones and scope

## Stack

- **Backend:** Go 1.26, Wails v3.0.0 (`github.com/wailsapp/wails/v3`), module name `pakpos`
- **Frontend:** React 19, TypeScript 6, Vite 8, Tailwind CSS v4, shadcn/ui (`radix-nova` style), Zustand, lucide-react, sonner
- **Planned (not yet added):**
  - CodeMirror 6
  - `modernc.org/sqlite` (pure Go, no CGO)
  - YAML workspace files with ULID IDs
  - goja for scripting
  - `zalando/go-keyring` for secrets
- **Targets:** Linux (WebKitGTK), macOS, Windows

## Commands

Run from the repo root. `wails3 task` is the bundled Task runner, so no separate `task` install is needed.

| Command | Purpose |
|---|---|
| `wails3 dev` | Run the app with hot reload |
| `wails3 build` | Production build to `bin/pakpos`. Also generates TS bindings. |
| `wails3 task test` | Go and frontend tests |
| `wails3 task coverage` | Tests with coverage gates. **Must pass (≥ 80%).** |
| `wails3 task lint` | gofmt, go vet, golangci-lint (skipped if not installed), tsc, ESLint, Prettier |
| `wails3 generate bindings -ts` | Regenerate `frontend/bindings` after changing bound Go services |

Frontend only (run in `frontend/`): `npm test`, `npm run coverage`, `npm run typecheck`, `npm run lint`, `npm run format`.

Before you finish a task, run `wails3 task lint` and `wails3 task coverage`, and make sure both pass.

## Repository layout

```
main.go                  Wails bootstrap, registers services; keep it minimal
internal/
  service/               Wails-bound services: thin adapters only
  buildinfo/             Version info (set via -ldflags)
  core/...               (planned) model, vars, auth, httpexec, script, curl, codegen
  store/...              (planned) fsstore (YAML workspace), sqlite (history/settings)
  secrets/               (planned) keychain wrapper behind an interface
frontend/
  src/components/ui/     shadcn components, vendored; see "Frontend conventions"
  src/features/<area>/   feature UI (shell, request, response, ...)
  src/stores/            Zustand stores
  src/hooks/, src/lib/   shared hooks and pure helpers
  src/test/setup.ts      Vitest setup and jsdom polyfills
  bindings/              generated by wails3; never edit, gitignored
build/                   Wails packaging assets and platform Taskfiles
scripts/go-coverage.sh   Go coverage gate
docs/                    architecture and plans
```

## Architecture rules

- **Packages under `internal/core` and `internal/store` must never import Wails.** Wails code lives only in `main.go` and `internal/service`. This keeps the core unit-testable and leaves room for a headless CLI runner later.
- **Services are thin.** They translate between Wails and core packages and contain no business logic.
- **HTTP requests are always sent from Go (`net/http`), never from the webview.** This avoids CORS and gives full control over TLS, proxies and cookies.
- **Workspace data is plain files, one request per YAML file**, so diffs stay small for git. History and app state go in SQLite.
- **Secrets never go into workspace files.** Files store a reference; the value lives in the OS keychain.
- **Prefer pure-Go dependencies (no CGO)** so cross-compilation stays simple.
- **Keep the planned Tier 2 fields** (`auth.type: inherit`, `seq`, variable scopes) in models even before they are used. This avoids a file format migration later.

## Go conventions

- Code must be `gofmt`-clean and pass `go vet`. Use table-driven tests.
- Use `httptest.Server` for HTTP tests, `t.TempDir()` for filesystem tests, in-memory SQLite for store tests, and fakes behind interfaces (keychain, clock).
- Return errors with context (`fmt.Errorf("open workspace %q: %w", path, err)`). Do not panic in library code.
- Pass `context.Context` through anything that does I/O or can be cancelled.
- Bound service methods should use JSON-tagged DTO structs so the generated TS types stay clean.

## Frontend conventions

- Import from `src` using the `@/` alias.
- **`src/components/ui/` holds vendored shadcn code**, added with `npx shadcn@latest add <name>`. It is excluded from lint, Prettier and coverage. Keep edits there minimal.
  - Known edit: `sonner.tsx` uses `useResolvedTheme` instead of `next-themes`.
  - These components import `cn` from the npm package `cn` (shadcn's official one). App code imports it from `@/lib/utils`.
- **Colors come only from theme tokens in `src/index.css`.** Do not hardcode hex values in components.
  - Use `bg-background`, `text-muted-foreground`, `bg-sidebar`, `text-primary`, and so on.
  - HTTP method colors: `text-method-get|post|put|patch|delete|other`, applied with `methodTextClass()` from `@/lib/http`.
  - Light and dark themes are both required. Dark mode is the `.dark` class on `<html>`, applied by `useResolvedTheme`.
- **Fonts:**
  - IBM Plex Sans (`font-sans`) for the UI.
  - JetBrains Mono (`font-mono`) only for content that is code: URLs, bodies, headers, method badges. Do not use it for decorative labels.
- **Design voice:**
  - It's a dense, quiet tool UI; the URL bar and method colors are the only accents.
  - No gradients or decorative shadows.
  - Write copy in sentence case, plain and active. Name buttons by what they do ("Send", "Save request").
  - Empty states tell the user what to do next. Error messages say what went wrong and how to fix it.
- **Accessibility:**
  - Every icon-only control needs an `aria-label` (and a tooltip).
  - Keep focus states visible.
  - Respect `prefers-reduced-motion`, which `index.css` already handles globally.
- Component state goes in Zustand stores (`src/stores`). Persist only UI preferences to `localStorage`. Real data comes from Go services.

## Testing

- **New code needs at least 80% coverage, for both Go and the frontend.** CI-style gates are enforced by `wails3 task coverage`; the thresholds are in `vite.config.ts` and `scripts/go-coverage.sh`.
- Use Vitest with jsdom and React Testing Library with `user-event`. Query by role and accessible name, not by class or test ID.
- jsdom quirks are handled in `src/test/setup.ts`:
  - It polyfills `matchMedia`, `ResizeObserver`, `PointerEvent` and the pointer-capture APIs.
  - It **mocks `@/components/ui/resizable` with plain divs**, because react-resizable-panels hit-tests by geometry and in jsdom (where every rect is 0×0) it captures every click. Keep this mock.
- The Wails Vite plugin is disabled under Vitest (`process.env.VITEST`), because it requires generated bindings.
- Mock Wails bindings in frontend tests. Never call real Go services from Vitest.

## Gotchas

- `frontend/bindings` only exists after `wails3 build`, `wails3 dev` or `wails3 generate bindings`. A plain `vite build` fails without it.
- `go vet ./...` at the root fails until `frontend/dist` exists, because of the `//go:embed`. Lint tasks run `go vet ./internal/...`.
- npm prints `Unknown project config "minimum-release-age"`. This comes from `frontend/.npmrc` (a supply-chain guard for pnpm/bun) and is harmless.
- `@wailsio/runtime` is pinned to exactly `3.0.0` to match the Go module. Upgrade both together.
- The Linux webview is WebKitGTK. Avoid bleeding-edge CSS and check rendering on Linux.
